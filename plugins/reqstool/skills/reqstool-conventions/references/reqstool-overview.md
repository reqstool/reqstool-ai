# reqstool Overview

For an overview of reqstool concepts (architecture, imports, filters, implementations), see this document.

## What is reqstool?

reqstool is a requirements traceability tool that connects requirements (YAML) → code annotations → test results, giving you end-to-end traceability from specification to verified implementation.

CLI: `reqstool {status,report,export} {local,git,maven,pypi} -p <path>`

`status` exit code = number of failures (0 = all requirements traced and verified).

## Architecture: system → microservice → external

reqstool uses a three-level architecture controlled by the `variant` field in `requirements.yml`:

| Variant | Role |
|---------|------|
| `system` | Defines requirements and SVCs. Has `implementations` pointing to microservices. This is the single source of truth (SSOT) for all requirements. |
| `microservice` | Has `imports` (pulls requirements/SVCs from system), own requirements/SVCs, and `filters` to scope imported IDs to what's relevant. |
| `external` | External requirement sources imported by system or microservice. |

## YAML files and their roles

| File | Where | Purpose |
|------|-------|---------|
| `requirements.yml` | system + microservice | Defines requirements; system-level has `implementations`; microservice-level has `imports` + `filters` |
| `software_verification_cases.yml` | system + microservice | Defines SVCs; microservice-level has `filters` for imported SVC IDs |
| `manual_verification_results.yml` | microservice | Results of manual verification |
| `reqstool_config.yml` | microservice | Tells reqstool where to find annotations and test results (paths relative to config file) |
| `annotations.yml` | build output | Generated by build plugins — maps code locations to requirement/SVC IDs (do NOT hand-edit) |

## Imports

How a microservice pulls requirements from a system:

```yaml
imports:
  local:
    - path: ../sys-001       # relative path to system reqstool dir
  # Also supports: git, maven, pypi sources
```

## Filters

How a microservice scopes down to only the relevant IDs:

```yaml
# In microservice requirements.yml — filter imported requirements by URN
filters:
  sys-001:                    # URN of the imported system
    requirement_ids:
      includes: [REQ_001, REQ_002]   # only import these (OR use excludes:)

# In microservice software_verification_cases.yml — filter imported SVCs
filters:
  sys-001:
    svc_ids:
      includes: [SVC_001, SVC_002]
```

## Implementations

How a system points to its microservices:

```yaml
# In system requirements.yml (variant: system only)
implementations:
  local:
    - path: ../ms-001        # relative path to microservice reqstool dir
  # Also supports: git, maven, pypi sources
```

## reqstool_config.yml

Tells reqstool where build-generated files live:

```yaml
language: java
build: gradle
resources:
  annotations: ../../build/reqstool/annotations.yml
  test_results:
    - ../../build/test-results/**/*.xml
```

## Cross-URN references

SVCs can reference requirements from other URNs using `urn:id` format:

```yaml
requirement_ids: ["REQ_010", "ext-002:REQ_ext002_400"]
#                  ^local     ^cross-urn (urn:id format)
```

## Processing flow

When you run `reqstool status local -p <path>`:

1. Read `reqstool_config.yml` at path (if present) for file location overrides
2. Read `requirements.yml` — note variant, imports, implementations, filters
3. Follow imports sequentially (local/git/maven/pypi), apply filters
4. Follow implementations to find microservice annotation and test result files
5. Collect annotations (generated by build plugins) and test results (JUnit XML etc.)
6. Compute traceability: every requirement has implementation annotation? has SVC? SVC has passing test?
